# DTS sign-in (experimental)

Unrelated to the live results. It lives in this repository only because it is hosted with it: one more service in the same image, deployed with the same `[deploy]` flow. What it must do is in [`src/dts/SPECS.md`](../src/dts/SPECS.md).

A DTS race-day XML is uploaded once. The upload answers with two secret links:

| Link | Key | Can |
| --- | --- | --- |
| `/dts/sign#<id>.<key>` | sign key | sign riders and change one field at a time (signed, cap number, transponder 1 and 2, race), add competitors, add notes, export |
| `/dts/manage#<id>.<key>` | manage key | watch the state, add and resolve notes, set the cutoff minutes per race, download the export per race |

The keys are in the URL fragment, so they are not sent to the server or written to logs; the server keeps the manage key as a hash only and the sign key in clear, so `/dts/` can show the sign link again.

- **Offline first.** The sign page keeps the XML and its log on the device and works without internet. It sends its operations and its action log when it can, and recreates the session on the host from its own copy if the host lost it.
- **State is a log.** The current state is the uploaded XML with the operations replayed over it. Cap number and transponder collisions are warnings, never blocks.
- **Several signers.** Any number of devices (`DTS_MAX_DEVICES`) can use the sign link at once. Each has an id and a name, pushes and pulls in one sync call, and the log replays to the same state everywhere; a rider already signed by another device shows who did it.
- **Basic auth on the manage page.** With `DTS_MANAGE_PASSWORD` set (as a secret; user `DTS_MANAGE_USERNAME`, default `manage`), nginx asks for a username and password on `/dts/manage`, to keep abuse away. The sign page and `/dts-api/` are not behind it; the keys protect the sessions. The passwords and the admin secret must be at least 16 characters (the container refuses to start otherwise), and the three password-protected locations allow a client address 30 requests a minute (burst 60), because basic auth has no lockout. The ids are 128 and the keys 256 random bits, so they cannot be guessed; the sign key travels in the URL fragment, which no server or referrer sees. Deleting a list in the admin page removes its whole folder (source, operations, actions, notes) and is remembered, so a device's copy cannot bring it back; a device that hears of the deletion erases its own copy too.
- **Retention.** A session is deleted a week after it was last used.
- **Personal data.** The XML holds names and licence numbers. It stays on the data volume and on the sign device, never in logs or in the repository; test data is generated.
- **Settings.** `DTS_LISTEN_ADDR`, `DTS_DATA_DIR`, `DTS_MAX_UPLOAD_BYTES`, `DTS_MAX_SESSIONS`, `DTS_RETENTION_DAYS`, `DTS_DEFAULT_CUTOFF_MINUTES`, `DTS_MAX_DEVICES`, `DTS_CREATES_PER_HOUR`, `DTS_CREATES_BURST`, `DTS_TIMEZONE` (the zone of the race start times, default Europe/Amsterdam), `DTS_CLIENT_IP_HEADER`, `DTS_ADMIN_SECRET`. In the image the client address for the rate limits (nginx and the service) comes from the header `BACKEND_CLIENT_IP_HEADER` names, shared with the live results (`Do-Connecting-Ip` on App Platform), and from the connection (nginx) or `X-Forwarded-For` (service) without one. In the image the service listens on loopback port 5002, nginx proxies `/dts-api/` to it, and `DTS_DATA_DIR` defaults to `/data/dts`; mount a volume there to keep sessions across deploys.

## Pages

The pages are their own Angular application (`src/frontend/src/dts-app`, project `dts` in `angular.json`), built to `dist/dts/browser` and copied to `/dts/` in the image, so the dashboard bundle carries none of it. The sign page is about 56 kB gzipped.

- **Admin page** (`/dts/`): a browser-sized page with four example graphics (upload, scan, sign, overview), a button to start a new list and every list on the server (races, devices, changes, last used) with a Delete button and a Details button. The page lists no signing devices. Delete is permanent: the list is removed from the server and remembered for 90 days, so a device that still has a copy cannot restore it (the service answers 410 and the sign page says the list was deleted). The page is behind basic auth (`DTS_ADMIN_PASSWORD`, user `DTS_ADMIN_USERNAME`, default `admin`; without a password nobody gets in). Its API, `GET /dts-api/admin/sessions` and `DELETE /dts-api/admin/sessions/<id>`, needs `Authorization: Bearer <DTS_ADMIN_SECRET>`: nginx checks the login first and adds the header, so the browser never holds the secret; without the secret the API is off (404). Signers never see this page and cannot start a list; they use the open session API with their keys. `/dts` redirects to `/dts/`.
- **Sign page** (`/dts/sign`): made for a phone, one competitor at a time, large type, Dutch or English. It shows the sign link as a QR code for a second phone. It can be added to the home screen (web app manifest `public/dts.webmanifest`); a launch without a link in the address reopens the session this device used last. A service worker (`public/dts-sw.js`, scope `/dts/`) keeps the last copy of the page and the hashed script files, so a reload on a bad connection still opens. The API and everything outside `/dts/` always go to the network. Where the browser offers it, the page asks to add itself to the home screen, because Safari drops site data after a week otherwise.
- **Manage page** (`/dts/manage`): made for a laptop or monitor. The races are stacked vertically, each across the full width. Riders are shown as leg number chips without names: green when signed, purple when signed with a change, yellow when there is a note (a legend sits on the page). The tab title names the page.
- **Rate limits.** Only failed attempts count, per client address: a wrong session key or admin secret, an upload or restore that is refused as invalid, too big or conflicting. Ten in a row, then thirty an hour; while used up, even a right key from that address gets 429 with `Retry-After`. Other calls are never limited. New sessions (an upload or a restore) are limited per client address too: ten back to back, then thirty an hour (`DTS_CREATES_BURST`, `DTS_CREATES_PER_HOUR`); `DTS_MAX_SESSIONS` caps the total.
- **Transponder images.** The sign page shows a red transponder next to transponder 1 and a blue one next to transponder 2 (decorative, the text stays).
- **Several sessions on one device.** Each session is its own copy in IndexedDB. The address holds the session as `?s=<id>` (never the key) and the language as `?lang=`, so a bookmark or reload returns to it; `?new=1` starts another, and the home screen lists the others to switch to. The same session in two tabs is merged on every save.
- **Cleared site data.** If the copy vanishes while the page is open, the page says so and writes it back from memory; if the address names a session the device no longer has, the page says the data is gone and asks for the full link. What was already sent to the host is kept.
- **Race titles and file names.** A race is shown as `<place> - <name> - HH.mm uur - <category>` from the `Plaats`, `Start`, `Naam` and `Categorie` fields of the file (the time is the start as written in the file), for example `Deventer - Regio NoordOost 3 - 17.30 uur - NO-1`. A missing place, name or category is left out. Downloads use the same title in the file name. The title comes from the server, so it does not follow the page language.
- **Closing a race.** On the list details page (`/dts/list?s=<id>`) the admin can close a race of a list (`PUT /dts-api/admin/sessions/{id}/races/{race}` with `{"closed": true}`) and reopen it. For a closed race the server drops changes to its competitors, competitors added to it and moves into it; the sign page shows the race as closed and offers no changes.
- **Sign page screens.** The screen is part of the address (`view`, `race`, `rider`, `field`; the key stays in the hash), so back and reload work. Each race card has a "+ Nieuw" badge first, which starts the add flow with the race fixed. Numbers are listed by start number with the signed ones last, slightly greyed, and the tick keeps its width. The log is an expandable section. Input is limited in length (names count characters, not bytes).
- **List details.** The admin page links each list to `/dts/list?s=<id>`: the manage overview for the admin, with the race downloads. The admin sees no cutoff form; notes are per race in an expandable with a count; start dates that look wrong are shown above the race card and can be dismissed (remembered on the device). The header shows a "last change" pill with a dot (green, yellow after 5 minutes, red after 15) and a relative time. A "+ Nieuw" badge opens the sign page add flow for a race, using the sign key the admin API exposes. A start number opens the competitor page (`&c=<entry>`), laid out like the signer's rider screen, whose badges link to the sign page edit screens; entries in the latest actions (shown as start number and name) link there too. At the bottom the signing devices are listed with a relative last-seen time, how many they signed and how many other changes they made, and a Remove button (`DELETE /dts-api/admin/sessions/{id}/devices/{device}`; the device is listed again when it syncs; the changes are kept). Titles carry instant multi-line tooltips. "Download tekenlijst (PDF)" renders the signing list in the layout of the paper list (a grid of number boxes per race with the transponders and the name; a changed number or transponder is shown struck through next to the new value, a signed one gets a tick; the licence number is in the top left corner), written in the browser by `dts-pdf.ts` without a library, followed by the whole action log on separate pages. **Requirement:** the PDF must stay readable on a grayscale print. Text, borders and marks are told apart by weight, dash pattern, labels and brightness and never by colour alone; the colours are chosen so that, converted to gray, text keeps a contrast of at least 4.5:1 and borders 3:1 against the cell fills, and the signed tick shows on its fill. `dts-pdf.spec.ts` checks this. For that it reads `GET /dts-api/admin/sessions/{id}?log=all`, which carries every action instead of the latest 20, and the `orig` number and transponders of the uploaded file on changed entries. It reads `GET /dts-api/admin/sessions/{id}` and `GET /dts-api/admin/sessions/{id}/export?race=` behind the same login and secret.
- **Sign link.** The link and QR code to sign are shown again on `/dts/` for every list, from the admin API. A list made before the server kept the sign key shows none until a device syncs it.
- **Two signers on one competitor.** When another device changes the cap number, a transponder or the race of the competitor on screen, the page says who did it. The latest change (by corrected time, then id) wins.

## Export for MDS

- `GET .../export?format=tekenlijst` gives the XML for "Tekenlijst verwerken" in MDS: one row per signed rider with a licence number. Unsigned riders are left out, because MDS lists every unsigned row in its "Scan&Go tekenlijst" dialog. A known side effect: a rider who is still unsigned after the first import stays unsigned in MDS, and an unsigned rider's transponder change is not carried over. This is accepted as not a real situation.
- `GET .../export?format=mdsnew` gives a text file with the racers added during the day, for the Import button on the Deelname tab of the race. It is the format of the MDS import spec `ImportBeennummer`: one line per racer, delimited, in Windows-1252 with CRLF, the fields each in double quotes and separated by semicolons, in the order start number (4), licence number (8), team (left empty), transponder 1 (25), transponder 2 (25), name (45): `"A122";"ZZ00001";"";"XX-12341";"";"Name"`. A racer without a licence number gets a placeholder `ZZ00001`, `ZZ00002`, ...; MDS makes a licence holder of it from the name. Letters are folded to ASCII and a double quote in a value becomes a single quote. A start number, transponder or licence number that does not fit its field is refused with 422; a longer name is cut.
- A fixed-width line is read by MDS as one field and imports nothing ("0 deelnemers overgenomen").

## Development and tests

- `dev-services.sh` starts the service on port 5002 with a temporary data directory and the DTS pages with `npm run start:dts` (port 4201); the dashboard dev server proxies `/dts-api` to the service and `/dts/` to the pages.
- `go test ./...` in `src/dts` runs the service tests; `ng test` runs the pure frontend logic and the QR encoder.
- Playwright specs `src/frontend/e2e/dts-*.e2e.ts` (sign, manage, sync and restore, install, accessibility with axe) run on `chromium` with the other specs. They start their own service on port 15002. `DTS_BROWSERS=1 npx playwright test dts- --project=firefox` (also `webkit`, `msedge`, and `dts-phone`/`iphone` for a phone viewport with touch) runs them in other browsers, on demand and not in CI.

## Not built

- Server-sent events (the pages poll).
- Competitors added by a signer, other than a rider already in the file, are exported as a `DTS_Deelname` row with their start number and transponders but an empty `Wedstrijdnummer` (the licence number, 8 digits such as 10154197): what was typed is free-form input and is never written as one. No `DTS_Licentiehouder` record is written for them. Whether the DTS import accepts such a row is still to be checked.
