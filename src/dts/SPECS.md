# Specifications: DTS sign-in
Experimental part, unrelated to the live results. It is in this repository only because it is hosted with it: its own Go service (`src/dts`) and its own pages in the frontend, shipped in the same image and deployed with the same `[deploy]` flow.
Mark a new or changed spec `[ ]` (TODO); once it is built and verified, mark it `[x]`.
Data specs are verified by unit tests (`*_test.go`, `*.spec.ts`), UI specs by Playwright e2e specs. Test data is generated and anonymised; a real export never enters the repository.

## Service (`src/dts`)

### Sessions
- [x] Go, standard library only; its own module and test suite; built as a stage of `prod/Containerfile`; runs as an s6 service on loopback (`DTS_LISTEN_ADDR`, default `127.0.0.1:5002`); nginx proxies `/dts-api/` to it; `DTS_DATA_DIR` (default `/data/dts`) holds the sessions; without a data directory the service is off
- [x] Only management creates a list: `POST /dts-api/admin/sessions` (admin secret) with a DTS XML (size cap `DTS_MAX_UPLOAD_BYTES`, default 5 MiB) parses and validates it (the checks of `.agents/DTS.md` section 4 become warnings in the answer, a file that is not a DTS export is refused with 422) and answers `{id, signKey, warnings}`; the sign key is a random 256-bit value (the page shows it as the sign link and QR code, and the admin API shows it again); the public API has no create endpoint
- [x] Failed attempts (wrong keys, refused uploads) are rate limited per client address (`DTS_CLIENT_IP_HEADER`, IPv6 by /64) with a token bucket; successful requests are not. At most `DTS_MAX_SESSIONS` sessions in total; blocked addresses get 429 with `Retry-After`, a full service 503
- [x] Two roles with nothing in common: the **signer** (sign key, kept as a SHA-256 hash and in clear for the admin to show again) may read, append operations and actions, add notes and export; the **admin** (the admin secret, `Authorization: Bearer`, checked by every `/dts-api/admin/` endpoint) may create and delete lists, read them, append operations (stored under the device name `sysadmin`), add notes, set the cutoff minutes and close races. A per-session manage key hash is kept only for the device restore and opens no endpoint; the public API gives it 404 everywhere; a key is sent as `Authorization: Bearer`, compared in constant time, and never appears in a URL path or query (the pages carry it in the fragment, which the browser does not send); a wrong key and an unknown session both answer 404
- [x] A session is deleted `DTS_RETENTION_DAYS` (default 7) after its last write or read; `DELETE /dts-api/sessions/{id}` with the sign key removes it at once; nothing of a session is logged beyond its id

### Operations and state
- [x] The state is the uploaded XML plus an append-only log of operations, each with a client-made id, a client timestamp and its arguments. **One operation changes one field of one racer**: `sign` (signed yes or no, with the signing time), `cap` (the start number), `transponder1`, `transponder2` (empty removes it), `race` (moves the entry to another race, keeping its other fields), and `add-racer`. A racer's `note` is not an operation on the data (see Notes and actions). The current state is the replay of the log over the XML
- [x] A cap number matches `^[A-Z]?[0-9]{1,3}$` (so `7`, `X3`, `W81`, `123`); a transponder matches `^[A-Z]{2}-[0-9]{5}$`; an operation with a value that does not match is refused with 422 and stored nowhere
- [ ] `add-racer` adds a racer to a race by a free-form name or a licence number, with cap number, transponder 1, optional transponder 2 and signed. A licence number that is in the file uses that rider; otherwise the racer is stored as an added racer (name or licence number as typed, flagged as added) and the export writes its `DTS_Deelname` row with an empty `Wedstrijdnummer` (see Export). The operation's id becomes the racer's entry id and must not be the id of an existing entry: such an operation is rejected on replay
- [x] `POST /dts-api/sessions/{id}/operations` (sign key) appends a batch; an id already present is skipped, so a retry is harmless
- [x] Replaying is deterministic and order independent for the same set of operations (sorted by client timestamp, then id); two devices that signed the same rider converge
- [x] `GET /dts-api/sessions/{id}` (either key) answers the state: per race the start, cutoff, counts, who is signed with their time, who is unsigned, the late list with minutes late, the warnings and the notes; `GET /dts-api/sessions/{id}/log` (sign key) answers the whole operation log
- [x] The cutoff is the number of minutes before a race's start at which signing closes: 30 for every race unless set otherwise (`DTS_DEFAULT_CUTOFF_MINUTES`, default 30). The manage page sets it per race (0 to 240 whole minutes; removing the setting returns the race to the default) with `PUT /dts-api/admin/sessions/{id}/cutoff` (admin, body `{race, minutes}`); a change takes effect for signing from then on and never changes a signature already stored. It is part of the state, so the sign page receives it with every sync, keeps the latest value on the device for offline use, and checks a signature against it from the signing time; a late signature is stored with its minutes late and whether it was overridden. Each change is an entry in the action log with the old and new value and who set it
- [ ] `GET /dts-api/sessions/{id}/export` (either key) answers `DTS_<date>_updated.xml` written at text level as `.agents/DTS.md` section 6 says (untouched records byte for byte, the `generated` timestamp updated), after the server has re-parsed it and diffed it by key against the source; a difference that no operation explains fails the export. An added racer whose licence number is not in the file gets a `DTS_Deelname` row with its start number and transponders and an empty `Wedstrijdnummer` (the licence number, 8 digits such as 10154197, is free-form input when typed and never written); no `DTS_Licentiehouder` record is written for it
- [x] `GET /dts-api/sessions/{id}/export?race=<id>` answers the same kind of file for one race: `DTS_<date>_<race code>_updated.xml` with that race's `DTS_Wedstrijd`, its entries as they are now, and the `DTS_Licentiehouder` records those entries need (a rider in two races is in both files), in the order and form of the source, passing the same re-parse and diff check; an unknown race is 404. The files of all races together hold every entry exactly once

### Collision warnings (warn, never block)
- [x] After every operation the state is checked, and the result is part of the state as a list of warnings, each with a level, the racers involved (race, cap number, surname) and the value
- [x] The same rider (licence number) may have an entry in more than one race, and that is never a warning; only the cap number and transponder rules below apply
- [x] **Severe**: the same cap number twice in one race (also when a move to another race causes it); the same transponder code twice in one race (in either slot, on any two entries)
- [x] **Light**: the same transponder code in two different races. Cap numbers in different races are never a warning
- [x] A warning goes away by itself when the cause is changed; an operation is never refused for a collision, and the racer who causes it is told on the sign page with the other racer named

### Notes and actions
- [x] A **note** belongs to a racer and has a level (`note` or `warning`), a text (at most 200 characters), who set it (manage or sign), a time, and whether it is resolved. The manage page and the sign page both add notes and both can resolve them (for example "payment due", "check licence"); `POST /dts-api/sessions/{id}/notes` (sign key) or `POST /dts-api/admin/sessions/{id}/notes` (admin), the note recording which of the two set it. An unresolved note is shown on the sign page the moment that racer is on screen, a warning in amber with a large symbol and words
- [x] The sign page adds a leveled note to the racer on screen as one guided step (level in two big buttons, text, confirm), and resolves one with one button
- [x] The sign page's **racer note** is a free text on the racer that is only written to the action log, not to the data and not to the export
- [x] The sign page keeps an **action log** of everything it does, on the device and in order: each operation, each undo, each cap, transponder and sign change with the old and new value, each racer note, each warning shown and each override, each sync. It is sent on its own: `POST /dts-api/sessions/{id}/actions` (sign key) appends a batch, deduplicated by id like the operations, `GET` (sign key, or manage key) lists it. Both logs are kept when a session is restored

### Restore
- [x] `PUT /dts-api/sessions/{id}` with the sign key and a body of the original XML, the log and the hash of the manage key recreates a session the host no longer has (after a restart without a volume, or after the retention); it is refused with 409 when the session exists with another sign key, and is rate limited like an upload; on success the keys that worked before work again and the manage URL is unchanged
- [x] The state after a restore equals the state before it, byte for byte in the export

## Sign page (`/dts/sign#<signKey>`)

### Offline first
- [x] The page keeps the XML, the log, the keys and the cutoff settings in IndexedDB and works with no network at all after the first load; the app shell and the page code are cached by a service worker so a reload on bad internet still opens it
- [x] Every action is applied on the device first and put in an outbox; the sync (see Several signers) sends the outbox with a growing wait, and the page shows plainly whether everything is saved on the server (a big green "All saved" or an amber "Waiting for internet: 3 changes not sent yet")
- [x] When the server answers 404 for the session, the page restores it with `PUT` from its own copy, then carries on; when the server has operations the device lacks (another device), they are merged in
- [x] Asks the browser for persistent storage; on a device that refuses it the page warns once, in plain words, that the copy on this device may be lost, and carries on (it never refuses to start)
- [x] The first load takes the upload (a file picker, or the XML from the share/drop), creates the session, stores the keys, and shows both links, and the sign link as a QR code, for sharing

### Guided signing: one rider at a time, for people who are not technical
- [x] One screen, one rider: the cap number in very large type (at least 4rem), the surname and first name large, the race, and one thing to do; at most two big buttons (min 64 px high, full width) per step, with words rather than icons: "Yes, signed" / "Not here"
- [x] **Changes are made one field at a time**: signed, cap number, transponder 1, transponder 2 and racer note are each their own step with their own confirm, so each is one operation and one line in the log; the flow offers the next field but never changes two at once
- [x] A step by step flow (find the rider, confirm, sign, then optionally cap, transponder 1, transponder 2, note, next rider), a progress line ("12 of 31 signed in NO-2"), one undo that is always in the same place, and no menus or tables in the flow
- [x] Finding a rider: a large field for the cap number, with the matching racer shown on screen; typing a name part lists at most three matches as big buttons; nothing is changed before the rider is confirmed on screen
- [x] Adding a racer is its own guided flow, one question per screen: name or licence number (free form), race, cap number, transponder 1, transponder 2 (skip allowed), signed, a summary in plain words, then confirm; each answer is checked for its format at once, with a plain hint
- [x] Collision warnings show on the step that causes them, not as a block: severe in red with the other racer named ("Number 12 is already used by Vermeer in NO-2"), light in amber ("This transponder is also used in NO-3"), both with the buttons "Keep it anyway" and "Change it"; unresolved notes of the racer show first, with their level
- [x] After the cutoff the screen turns amber and says in one sentence what is the matter and what the two choices do ("The race starts in 20 minutes. Signing closed 10 minutes ago. Sign anyway?"); never a bare error
- [x] The **action log** is shown next to the racer in progress (the latest actions for this racer, large enough to read, newest first) and on the main screen in a smaller size (the latest actions of the session, with a way to show all)
- [x] Respects the accessibility skill: contrast of at least 7:1 for the main text, focus visible, reduced motion, works at 200% zoom and in portrait on a phone and landscape on a tablet, screen reader labels, and never colour alone
- [x] Text in Dutch (the default) and English only, switchable on the page; all strings in one typed file per language, with a spec that both carry the same keys

## Phones
- [x] The sign page is designed for a phone first, in portrait, used with one hand and a thumb: the actions sit in the lower half of the screen, buttons are at least 64 px high with 12 px between them, no hover, no drag, no double tap, no text smaller than 16 px (so Safari does not zoom into a field), the cap field opens the text keyboard in capitals, because a cap number may start with a letter, and `viewport-fit=cover` with safe-area insets for notches; tablets and desktops get the same layout, centred and wider
- [x] Built for bad mobile networks and a screen that goes dark: every request has a timeout and a retry with a growing wait; a request that fails never loses an action; the page syncs again at once on `online`, on `visibilitychange` to visible and on `pageshow`; it does not depend on a background tab running, and it asks for a screen wake lock where the browser has one, working without it
- [x] Works as a web page and when added to the home screen (a web app manifest and icons, `display: standalone`); on iOS Safari, which removes site data after seven days without a visit unless the page is on the home screen, the page says once that adding it to the home screen keeps its copy, and the server mirror (Restore) covers the rest
- [x] Small download: the DTS pages are their own Angular application, so the first visit loads about 56 kB gzipped for the sign page and nothing of the dashboard; nothing blocks the first screen
- [x] Opening the link on a second phone is easy: the sign page shows a QR code and a "Share" button (feature detected, falling back to copy) for its own link, with the key, for another signer, and says in one sentence that anyone with the link can sign
- [x] e2e specs run with a phone viewport (and touch) as well as a desktop one, and check the 64 px target size, no horizontal scroll at 320 px width

## Several signers
- [x] Any number of devices may use the same sign link at the same time (`DTS_MAX_DEVICES` per session, default 10); each device makes a random `deviceId` on first use, keeps it in its storage, and lets the signer give a short name ("Desk 2"), which is stored with its operations, actions and notes
- [x] Operations, actions and notes get a sequence number from the server in the order they are stored. `POST /dts-api/sessions/{id}/sync` (sign key) takes `{device, name, since: {ops, actions, notes}, ops, actions, notes, clientTime}` and answers, in one round trip, what was stored (deduplicated by id) and everything the other devices stored after the given sequence numbers, with the new sequence numbers, the server time and the state; `GET /dts-api/sessions/{id}/sync?since=…` (manage key too, read only) answers the same without sending
- [x] A new device starts from `GET /dts-api/sessions/{id}/source` (sign key, the XML as uploaded) and a sync from sequence 0, so it needs nothing but the link; a device that was offline catches up the same way
- [x] The devices converge: they all replay the same set of operations in the same order (time, then id), so the state is the same everywhere once every operation has arrived; a test with three devices that send in different orders and drop requests asserts equal state and equal export
- [x] Clocks of phones differ, and the cutoff depends on the time of signing: every sync answer carries the server time, the device keeps the offset to its own clock (the middle of the request's start and end) and stamps new operations with its corrected time, keeping the raw device time as well; an offset is shown on the manage page when a device is more than 5 seconds off
- [x] Two signers who change the same field of the same racer: the later one (corrected time, then id) wins, and the other device shows a plain notice on that racer ("Signer 2 changed the cap number to 12") instead of silently flipping; two who sign the same racer at once is no conflict
- [x] A racer who is already signed shows who signed and when ("Signed by Desk 2 at 18:12") when it is opened again on any device, and "Yes, signed" is replaced by "Already signed" with a button to sign again only when that is meant
- [ ] Syncing while the page is visible is quick enough to prevent double work at a desk: every 4 seconds with a short wait, backing off to 30 seconds on failures and when nothing changed for a minute, and at once after any action; server-sent events are not built, polling alone is used; with `EventSource` available the page may use server-sent events (`GET /dts-api/sessions/{id}/events`, nginx without buffering) to learn that something changed, and polls when it is not; every browser works with polling alone
- [x] The manage page lists the devices of the session: name, last seen, how many operations each stored, and a clock-offset warning; it shows which device signed each racer

## Management pages (`/dts-admin/`, behind the admin login)
- [x] A separate application from the sign pages (own entry, own nginx location, no shared page, no link to a sign page): it creates lists (`/dts-admin/new`), watches them, writes notes and cutoffs, closes races, and adds and changes competitors (`/dts-admin/add`, `/dts-admin/edit`) through the admin operations endpoint; it never uses a sign key to act
- [x] Shows per race: start time, cutoff, signed and unsigned counts, the unsigned list, the late list, the collision warnings (severe first), the notes, the latest actions of the action log, a **last update** line (the time of the newest change in the session, e.g. "Last change 18:52:10, 2 minutes ago", in the viewer's local time) next to "last synced" of the sign page and "page refreshed at"; refreshes by polling `GET /dts-api/sessions/{id}` every 10 seconds, with a clear "last updated" and a stale warning after a minute
- [x] Per race a cutoff field (minutes before the start, default shown) with the resulting cutoff time next to it in clock time, a save button and a reset to the default; the new value is confirmed on screen with the time it was saved
- [x] A download button per race (and one for the whole file) that fetches the export of that race, named by the race code, with the time of its last change next to it; the sign page says when work is still unsent, because the download only holds what the server has
- [x] Adding a note: pick a racer (by cap number or name), a level (note or warning), a text; resolving it is one button; every note and its resolution is part of the action log
- [x] Meant for a laptop or monitor: races side by side and the lists in columns as far as the screen is wide, shrinking to one column in a narrow window, large counts, same contrast rules as the sign page

## Browsers and tests
- [ ] Works in current Chrome, Firefox, Safari (desktop and iOS) and Edge, using only features all four have: IndexedDB, service workers, `fetch`, CSS grid and custom properties; nothing Chromium-only (no File System Access, no Web Share target dependence, no `showPicker` reliance). Each optional feature (persistent storage, wake lock, clipboard, share) is feature-detected and the page works without it
- [x] No third-party runtime libraries for storage, QR or file handling where a small plain implementation does; the same code path on every browser, with no user-agent sniffing
- [ ] Playwright e2e specs for the sign and manage pages in `src/frontend/e2e` (generated sample file, a backend started by the config), run per batch of a few specs: upload and the two links, signing a rider, each single-field change, collision warnings, the cutoff and its override, notes from both pages, the action log, the per-race download, offline use (network off, then back on, with the outbox emptied), and a restore after the server lost the session. They run on the `chromium` project of the existing config; a `firefox`, `webkit` and `msedge` (Chromium with the Edge channel) project are added for these specs only, and run on demand, not in CI
- [x] Go unit tests for the service (`go test ./...`, also with `-race`) and Vitest-style unit specs for the pure frontend logic (collision text, cutoff arithmetic, the outbox), run in CI as checks

## Limits and privacy
- [x] The XML holds personal data: it is stored only on the data volume and in the sign device's IndexedDB, never in the log lines, the error messages, the metrics or the repository; the manage page shows riders by race, start number and surname
- [x] The pages and the API carry `Referrer-Policy: no-referrer`, `Cache-Control: no-store` for the API, and are excluded from search engines (`noindex`, no link from the live results pages)
